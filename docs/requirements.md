## 1. 기능 요구사항

### 1.1 사용자 및 조직 관리 (User)

#### US-01. 회원가입 및 로그인

| 항목 | 내용 |
|---|---|
| ID | US-01 |
| 사용자 스토리 | 사용자로서 가입하고 로그인해 서비스를 쓰고 싶다. |
| 수용 기준 | 가입과 로그인이 가능해야 하며, 첫 로그인 시 프로필이 생성된다. |
| 서비스 | user |
| API | `GET /api/users/me` |

#### US-02. 조직 생성

| 항목 | 내용 |
|---|---|
| ID | US-02 |
| 사용자 스토리 | OWNER로서 팀의 공간을 만들고 싶다. |
| 수용 기준 | 조직을 생성한 사용자는 해당 조직의 OWNER가 된다. |
| 서비스 | user |
| API | `/api/orgs` |

#### US-03. 초대 링크를 통한 팀원 초대

| 항목 | 내용 |
|---|---|
| ID | US-03 |
| 사용자 스토리 | OWNER로서 링크로 팀원을 초대하고 싶다. |
| 수용 기준 | 초대 링크를 수락하면 MEMBER가 되며, 추가 초대 없이 모든 협업 기능을 사용할 수 있다. 사용된 링크는 재사용할 수 없다. |
| 서비스 | user |
| API | `POST /api/invitations/{token}/accept` |

#### US-04. 조직 멤버 권한 회수

| 항목 | 내용 |
|---|---|
| ID | US-04 |
| 사용자 스토리 | OWNER로서 나간 팀원의 권한을 한 번에 회수하고 싶다. |
| 수용 기준 | 멤버가 탈퇴하거나 제거되면 5초 이내에 모든 조직 API가 해당 사용자에게 403을 반환한다. |
| 서비스 | user |
| API | `/api/orgs/{id}/members/{userId}` |

#### US-05. 조직 간 데이터 격리

| 항목 | 내용 |
|---|---|
| ID | US-05 |
| 사용자 스토리 | 멤버로서 우리 조직의 데이터를 외부로부터 보호하고 싶다. |
| 수용 기준 | 소속되지 않은 조직의 데이터에 접근을 요청하면 403을 반환한다. |
| 서비스 | 전체 |
| API | 조직 API 전체 |

### 1.2 채팅 및 파일 관리 (Chat / File)

#### US-06. 실시간 채팅

| 항목 | 내용 |
|---|---|
| ID | US-06 |
| 사용자 스토리 | 멤버로서 채널에서 실시간으로 대화하고 싶다. |
| 수용 기준 | 다른 파드에 연결된 사용자에게도 메시지가 1초 이내에 전달된다. (100건 측정) |
| 서비스 | chat |
| API | `GET /api/chat/channels?orgId=`<br />`WS /api/chat/ws` |

| 항목 | 내용 |
|---|---|
| ID | US-07 |
| 사용자 스토리 | 멤버로서 연결이 끊겨도 대화를 놓치고 싶지 않다. |
| 수용 기준 | 재연결하면 놓친 메시지가 순서대로 누락 없이 표시된다. |
| 서비스 | chat |
| API | `GET /api/chat/channels/{id}/messages?after=` |

#### US-08. 채널 내 파일 미리보기

|---|---|

| API | `GET /api/files/{id}/preview-url` |

#### US-09. 메시지를 칸반 카드로 변환

| 항목 | 내용 |
|---|---|
| ID | US-09 |
| 사용자 스토리 | 멤버로서 대화에서 나온 일을 바로 카드로 만들고 싶다. |
| 수용 기준 | 메시지를 기반으로 칸반 카드를 생성하면 메시지 내용이 카드에 포함되며, 카드에서 원본 메시지로 이동할 수 있다. |
| 서비스 | chat, board |

#### US-10. 결정 사항 기록

|---|---|

| 수용 기준 | 메신저 채널 내에서 메시지를 결정 로그 채널에 등록하면 작성자, 등록 시각, 원본 메시지 링크가 함께 저장된다. |
| 서비스 | chat |
| API | `POST /api/chat/messages/{id}/decision` |

#### US-11. 메시지 확인 여부 관리

| 항목 | 내용 |
|---|---|
| ID | US-11 |
| 사용자 스토리 | 멤버로서 꼭 봐야 할 사람의 확인 여부를 알고 싶다. |

| 서비스 | chat |
| API | `/api/chat/messages/{id}/acknowledgements` |

#### US-12. 조직 파일 관리

| 항목 | 내용 |
|---|---|
| ID | US-12 |
| 사용자 스토리 | 멤버로서 조직 파일을 한곳에서 관리하고 싶다. |

## 2. 비기능 요구사항(초안)

| 항목 | 요구 | 관련 설계 |
|---|---|---|
| 성능 | 일반 API 응답 시간 p95 500ms 이내<br />채팅 메시지 1초 이내 전달(US-06)<br />칸반 · 캘린더 변경 3초 이내 반영(US-15, US-20)<br />알림 5초 이내 발송(US-17, US-18)<br />회의방당 8명이 10분간 통화(US-22) | |
| 가용성 | 서비스별 파드 2개 이상<br />liveness · readiness 프로브로 장애 파드를 자동 재시작하고 트래픽에서 제외<br />Redis 장애 시 메시지는 저장되고 실시간 전달만 빠지며, 재연결하면 복구(US-07)<br />배포 문제는 `git revert`로 롤백 | 아키텍처 |
| 확장 | 채팅 파드가 여러 개여도 모든 사용자에게 메시지 전달(US-06)<br />서비스별로 독립해 파드를 늘릴 수 있음<br />다른 서비스 데이터는 ID로만 참조하고 서비스 간 외래 키와 JOIN 금지 | |
| 보안 | 외부 통신은 HTTPS · WSS만 허용<br />Gateway와 서비스가 모두 JWT 검증, 서비스 간 통신은 mTLS<br />소속되지 않은 조직의 데이터 접근은 403(US-05), 권한 회수는 5초 이내(US-04)<br />멤버십을 확인할 수 없으면 접근 차단<br />비밀값은 Git에 넣지 않고 Kubernetes Secret으로 관리 | 공통 규칙 |
| 관측 | 모든 서비스의 요청 수, 에러율, p95 응답 시간, CPU · 메모리 · 재시작 수를 Grafana에서 확인<br />모든 서비스가 같은 형식의 JSON 로그를 남기고 요청 ID로 추적<br />에러율 5%가 5분을 넘으면 알림 | 관측 설계 |
