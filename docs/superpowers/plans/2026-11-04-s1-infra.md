# S1 인프라 구축 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** PR을 자동 검사하는 CI 서버와, Git 변경을 자동 배포하는 k8s 클러스터를 만든다.

**Architecture:** CI 전용 VM에 Jenkins를 docker-compose로 띄워 PR의 변경 경로만 검증한다. 다른 VM들은 kubeadm과 Calico로 클러스터를 구성하고, Argo CD가 App of Apps로 `main`을 동기화한다. 서비스 배포는 S3에서 한다.

**Tech Stack:** Jenkins(JCasC), Docker Compose, yamllint, Helm, kubeconform, kubeadm, containerd, Calico, Argo CD

**Spec:** `docs/superpowers/specs/2026-11-03-mvp-design.md`

## Global Constraints

- 버전은 구현 시점의 최신 안정판으로 고정한다. `latest` 금지.
- 시크릿, 키, 토큰, kubeconfig는 커밋하지 않는다. 예시(`*.example`)만 둔다.
- 이름은 `kebab-case`, YAML 들여쓰기 2칸, k8s 리소스는 `namespace`를 명시한다.
- 클러스터를 손으로 바꾸지 않는다. 예외는 kubeadm, CNI, Argo CD 설치와 시크릿 생성이며 절차는 `deploy/cluster/`에 둔다.
- `helm install/upgrade`, `kubectl apply/delete`, `argocd app sync/delete`는 실행 전에 사용자에게 확인받는다.
- Task 하나 = PR 하나. 브랜치는 `<type>/<이슈번호>-<짧은-설명>`.
- 경로가 적힌 명령과 커밋은 저장소 루트에서 실행한다.

## S1에서 하지 않는 것

이미지 빌드와 GHCR push, 이미지 태그 PR 자동화는 첫 배포가 있는 S3에서, MetalLB, Istio 등은 S2부터 한다.

## 구현 전 선행 작업 (~11/8)

코드 작업이 아니라 Task로 두지 않았다. Task 2~4는 이 결과가 있어야 끝낼 수 있다.

- [ ] 제공처에 요청: 고정 공인 IP, 포트 포워딩(`443/TCP` → IP #1, `7881/TCP`, `7882/UDP`, `3478/UDP` → IP #2), CI 전용 VM
- [ ] Route 53 IAM 사용자 생성(해당 호스팅 영역만)
- [ ] VM에서 AWS API 아웃바운드 확인: `curl -sI https://route53.amazonaws.com` 응답 확인
- [ ] 저장소 주소와 VM 목록(IP, 사양)을 받아 아래 값에 넣는다. `<REPO_URL>`은 저장소 주소다.

## Review Focus

1. CI VM이나 클러스터 VM 재부팅: 손 작업 없이 복구되고 설정이 유지된다. (Task 2, 3, 4)
2. PR을 처음 올린 첫 빌드: 이전 빌드가 없어도 변경 경로를 정확히 찾는다. (Task 2)
3. 차트나 매니페스트가 아직 없는 저장소: `validate.sh`가 실패하지 않는다. (Task 1)
4. Jenkins 컨테이너와 볼륨을 지우고 다시 생성: 커밋된 설정만으로 같은 상태가 된다. (Task 2)
5. Git에서 앱을 되돌림: 클러스터의 리소스도 함께 사라진다. (Task 4)

### Task 1: 인프라 설정 검사 스크립트

**무엇:** 잘못된 YAML이나 Helm 차트를 머지 전에 찾아내는 스크립트를 만든다.

**Files:**
- Create: `deploy/scripts/validate.sh`, `deploy/.yamllint.yaml`
- Test: `deploy/scripts/validate_test.sh`

**Interfaces:**
- Produces: `deploy/scripts/validate.sh [deploy_dir]`. 기본값은 스크립트 기준 상위 `deploy/`. 문제가 없으면 종료 코드 0, 있으면 0이 아니다.

- [ ] **Step 1: 실패하는 테스트 작성**

`validate_test.sh`는 임시 폴더에 아래 입력을 만들어 종료 코드를 확인한다. 하나라도 어긋나면 `exit 1`.

| 케이스 | 입력 | 기대 |
| ---- | ---- | ---- |
| `empty_deploy_passes` | 빈 폴더 | 0 |
| `broken_yaml_fails` | 문법이 깨진 `a.yaml` | 0 아님 |
| `broken_yml_extension_fails` | 문법이 깨진 `a.yml` | 0 아님 |
| `invalid_deployment_fails` | `manifests/`에 `spec.replicas: "many"`인 Deployment | 0 아님 |
| `broken_chart_fails` | `charts/x/`에 템플릿 문법 오류 | 0 아님 |
| `argocd_application_passes` | `argocd/`에 정상 Argo CD `Application` | 0 |

- [ ] **Step 2: 테스트 실패 확인**

Run: `bash deploy/scripts/validate_test.sh`
Expected: `validate.sh`가 없어 FAIL

- [ ] **Step 3: `deploy/scripts/validate.sh` 구현**

순서: `yamllint -c deploy/.yamllint.yaml`로 `*.yaml`과 `*.yml` 전체 검사(`templates/` 제외) → `charts/*/`마다 `helm lint`와 `helm template | kubeconform -strict -ignore-missing-schemas` → `argocd/`, `manifests/`에 `kubeconform -strict -ignore-missing-schemas`. 대상이 없는 단계는 건너뛴다. `set -euo pipefail`을 쓴다. `.yamllint.yaml`은 `default`를 확장하고 `document-start`와 `line-length`를 끈다.

- [ ] **Step 4: 테스트 통과 확인**

Run: `bash deploy/scripts/validate_test.sh && bash deploy/scripts/validate.sh`
Expected: 6개 PASS, 종료 코드 0

- [ ] **Step 5: 커밋**

```bash
git add deploy/scripts deploy/.yamllint.yaml
git commit -m "ci: 인프라 검증 스크립트 추가"
```

### Task 2: Jenkins 서버와 PR 검증

**무엇:** CI 전용 VM에 Jenkins를 설치해, PR에 통과/실패가 표시되게 한다.

**Files:**
- Create: `Jenkinsfile`, `deploy/ci/compose.yaml`, `deploy/ci/Dockerfile.controller`, `deploy/ci/Dockerfile.agent`, `deploy/ci/plugins.txt`, `deploy/ci/jenkins.yaml`, `deploy/ci/.env.example`, `deploy/ci/README.md`

**Interfaces:**
- Consumes: `deploy/scripts/validate.sh`
- Produces: `CHANGED_FILES` 환경 변수와 `Validate deploy` 스테이지가 있는 `Jenkinsfile`. 서비스 계획의 CI Task가 스테이지를 추가한다.

**결정한 값:**
- 컨트롤러: `numExecutors: 0`, 플러그인은 `configuration-as-code`, `workflow-aggregator`, `github-branch-source`, `job-dsl`, `ssh-slaves`, `credentials-binding`.
- 에이전트: SSH로 연결한다. 이미지에 JDK, git, yamllint, helm, kubeconform을 버전 고정해 넣는다.
- 작업: JCasC `jobs`로 멀티브랜치 작업 `ideaconnection`을 만든다. 저장소는 `<REPO_URL>`, 스캔 주기는 2분.
- 빌드 대상: 저장소 안 브랜치의 PR과 `main`만. 포크 PR은 찾지 않는다. 그래서 쓰기 권한이 있는 사람의 PR만 빌드한다.
- 시크릿: `GITHUB_TOKEN`(상태 체크와 저장소 읽기), `AGENT_SSH_PRIVATE_KEY`, `AGENT_SSH_PUBLIC_KEY`, `JENKINS_ADMIN_PASSWORD`를 `.env`로 주입한다. push 토큰은 S1에 만들지 않는다.
- 두 컨테이너 모두 `restart: unless-stopped`, 컨트롤러는 `jenkins_home` 볼륨을 쓴다.

- [ ] **Step 1: 이미지와 compose 파일 작성 후 검사**

Run: `cp deploy/ci/.env.example deploy/ci/.env && docker compose -f deploy/ci/compose.yaml config -q && docker compose -f deploy/ci/compose.yaml build`
Expected: 오류 없음

- [ ] **Step 2: `Jenkinsfile` 작성**

`Detect changes` 스테이지: PR이면 대상 브랜치를 fetch해 `git diff --name-only origin/$CHANGE_TARGET...HEAD`로, `main`이면 `git diff --name-only HEAD~1 HEAD`로 `CHANGED_FILES`를 구한다. Jenkins의 `changeset` 조건은 첫 빌드에서 비어 있을 수 있어 쓰지 않는다. `Validate deploy` 스테이지: `deploy/` 변경이 있을 때만 `validate.sh`를 실행한다.

- [ ] **Step 3: CI VM에 실행**

Run: `docker compose -f deploy/ci/compose.yaml up -d`
Expected: Jenkins에서 에이전트 온라인, 컨트롤러 실행기 0개, `ideaconnection` 작업이 자동 생성됨

- [ ] **Step 4: PR 시나리오 확인**

임시 브랜치로 PR을 올려 확인하고, 확인 후 닫는다.

| PR | 기대 |
| ---- | ---- |
| `deploy/`에 깨진 YAML을 넣은 첫 빌드 | 2분 안에 상태 체크 실패 |
| 위 PR에서 YAML 수정 | 상태 체크 성공 |
| `docs/`만 바꾼 PR | 성공, `Validate deploy` 건너뜀 |

- [ ] **Step 5: 복구 확인**

VM을 재부팅한다. 이어서 `docker compose -f deploy/ci/compose.yaml down -v && docker compose -f deploy/ci/compose.yaml up -d`를 실행한다.
Expected: 두 경우 모두 에이전트 온라인, `ideaconnection` 작업 존재

- [ ] **Step 6: 문서 작성과 커밋**

`deploy/ci/README.md`에 준비(`.env`)와 실행 명령만 적는다. Step 4를 통과한 뒤 저장소 룰셋에서 이 상태 체크를 필수로 켠다.

```bash
git add Jenkinsfile deploy/ci
git commit -m "ci: Jenkins 서버와 PR 검증 추가"
```

### Task 3: k8s 클러스터 구성

**무엇:** 제공받은 VM들을 하나의 k8s 클러스터로 묶고, 파드끼리 통신하게 한다.

**Files:**
- Create: `deploy/cluster/README.md`, `deploy/cluster/kubeadm-config.yaml`, `deploy/cluster/calico-installation.yaml`

**Interfaces:**
- Produces: 모든 노드가 `Ready`인 클러스터와, 다른 팀원이 다시 실행할 수 있는 절차 문서

**결정한 값:**
- 노드: 컨트롤 플레인 1대, 나머지는 워커. CI 전용 VM은 넣지 않는다.
- 런타임은 containerd(`SystemdCgroup = true`), Pod CIDR은 `10.244.0.0/16`, Service CIDR은 `10.96.0.0/12`. VM 대역과 겹치면 Pod CIDR을 바꾸고 문서에 이유를 적는다.
- Calico는 Tigera Operator로 설치한다.

- [ ] **Step 1: VM 목록과 공통 준비를 문서화하고 실행**

`README.md`에 VM 이름, 역할, IP 표와 공통 준비를 적는다: swap 끄기, `overlay`와 `br_netfilter` 모듈, IP 포워딩, containerd, 버전 고정한 kubeadm/kubelet/kubectl.

Run(각 노드): `sudo kubeadm init phase preflight --config deploy/cluster/kubeadm-config.yaml`(컨트롤 플레인) 또는 `systemctl is-active containerd`(워커)
Expected: preflight 오류 없음, `active`

- [ ] **Step 2: 컨트롤 플레인 초기화와 Calico 설치**

사용자 확인 후 `kubeadm init --config`를 실행하고, Operator와 `calico-installation.yaml`을 적용한다.

Run: `kubectl get nodes && kubectl -n calico-system get pods`
Expected: 컨트롤 플레인 `Ready`, Calico 파드 `Running`

- [ ] **Step 3: 워커 추가 후 파드 통신 확인**

Run: 각 워커에서 `kubeadm join` 후, 서로 다른 노드에 임시 파드 2개를 띄워 `ping`
Expected: 모든 노드 `Ready`, `ping` 성공. 임시 파드는 지운다.

- [ ] **Step 4: 재부팅 복구 확인**

모든 VM을 재부팅한다.
Run: `kubectl get nodes && kubectl -n calico-system get pods`
Expected: 손 작업 없이 모든 노드 `Ready`, Calico 파드 `Running`

- [ ] **Step 5: 문서 완성과 커밋**

`README.md`에 실제 실행한 명령을 적는다. join 토큰과 kubeconfig는 적지 않는다.

```bash
git add deploy/cluster
git commit -m "docs: 클러스터 구축 절차 추가"
```

### Task 4: Argo CD 자동 배포

**무엇:** Git의 `main`에 머지한 설정이 클러스터에 자동으로 반영되게 한다.

**Files:**
- Create: `deploy/values/argocd/values.yaml`, `deploy/argocd/root.yaml`, `deploy/argocd/platform/.gitkeep`, `deploy/argocd/data/.gitkeep`, `deploy/argocd/services/.gitkeep`
- Modify: `deploy/cluster/README.md`(Argo CD 설치와 저장소 접근 절차 추가)

**Interfaces:**
- Consumes: Task 3의 클러스터, Task 1의 `validate.sh`
- Produces: `deploy/argocd/{platform,data,services}/`에 `Application`을 추가하면 자동 배포되는 구조. S2부터 사용한다.

**결정한 값:**
- 공식 Helm 차트를 `argocd` 네임스페이스에 버전 고정해 설치한다. S1의 접속은 `kubectl port-forward`로 한다(MetalLB는 S2).
- `root`: 저장소 `<REPO_URL>`, `targetRevision: main`, `path: deploy/argocd`, `directory.recurse: true`, `directory.exclude: root.yaml`, `syncPolicy.automated`의 `prune`과 `selfHeal`을 켠다.
- 저장소 접근은 읽기 전용 Deploy Key로 하고, 시크릿은 `kubectl create secret`으로 만든다.

- [ ] **Step 1: 설정 작성 후 검사와 커밋**

Run: `bash deploy/scripts/validate.sh`
Expected: 종료 코드 0

```bash
git add deploy/values/argocd deploy/argocd
git commit -m "feat: Argo CD 앱 구조 추가"
```

PR로 `main`에 머지한다. `root`는 `main`을 읽기 때문에 이 머지가 먼저다.

- [ ] **Step 2: Argo CD 설치와 root 적용**

사용자 확인 후 `helm install`, 저장소 시크릿 생성, `kubectl apply -f deploy/argocd/root.yaml`을 실행한다.

Run: `kubectl -n argocd get application root`
Expected: `Synced`, `Healthy`

- [ ] **Step 3: 자동 배포와 되돌리기 확인**

`deploy/manifests/smoke-test/`(네임스페이스 `smoke-test`와 ConfigMap)와 이를 가리키는 `deploy/argocd/platform/smoke-test.yaml`(`resources-finalizer.argocd.argoproj.io` 포함)을 PR로 머지한다.

Run: `kubectl -n smoke-test get configmap smoke-test`
Expected: 조회됨

머지 커밋을 `git revert`해 PR로 머지한다.
Run: `kubectl get namespace smoke-test`
Expected: `NotFound`

- [ ] **Step 4: 재부팅 복구 확인**

모든 클러스터 VM을 재부팅한다.
Run: `kubectl -n argocd get application root`
Expected: 손 작업 없이 `Synced`, `Healthy`

- [ ] **Step 5: 커밋**

실제 실행한 Argo CD 설치 절차를 문서에 적어 커밋한다.

