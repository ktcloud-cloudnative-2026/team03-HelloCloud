# S1 서비스 기반과 로그인 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 로컬에서 가입하고 로그인하면 프로필이 생기고 화면에 내 이름이 보인다(USER-1).

**Architecture:** 의존 구성 요소는 `compose.yaml`로 띄우고, `user-service`와 web은 호스트에서 실행한다. 브라우저가 Keycloak에서 OIDC + PKCE로 받은 JWT를 `user-service`가 검증한다. 공통 코드는 `libs/common`에 두고, `user-service`는 이후 서비스가 복사할 골격이 된다.

**Tech Stack:** Java LTS, Spring Boot, Gradle, Flyway, JUnit 5, Testcontainers, Spotless, React, Vite, TypeScript, react-oidc-context, Vitest, React Testing Library, Keycloak, MySQL 8.4

**Spec:** `docs/superpowers/specs/2026-11-03-mvp-design.md`

## Global Constraints

- 버전은 구현 시점의 최신 안정판으로 고정한다. `latest` 금지. MySQL은 8.4.
- 시크릿, 키, 토큰은 커밋하지 않는다. 설정은 환경 변수로 주입하고, 예시는 `.env.example`에 둔다.
- 사용자 ID는 Keycloak `sub`(UUID)를 그대로 쓴다.
- 에러 응답은 RFC 9457 Problem Details를 쓴다.
- lock 파일(`gradle.lockfile`, `package-lock.json`)을 커밋한다.
- Task 하나 = PR 하나. 브랜치는 `<type>/<이슈번호>-<짧은-설명>`.
- 커밋은 저장소 루트에서 실행한다. 다른 명령의 실행 위치는 각 Step을 따른다.

## S1에서 하지 않는 것

`libs/common`의 멤버십 클라이언트는 호출할 API가 생기는 S2에서, Dockerfile과 클러스터의 Keycloak은 첫 배포가 있는 S3에서 한다.

## 공통으로 쓰는 값

| 항목 | 값 |
| ---- | ---- |
| Keycloak | `http://localhost:8180/auth`, realm `ideaconnection`, client `web` |
| issuer | `http://localhost:8180/auth/realms/ideaconnection` |
| 로컬 포트 | user-service `8081`, web `5173` |
| database와 계정 | `user_service`, `board_service`, `file_service`, `chat_service`, `meeting_service` |
| 자바 패키지 | `com.ideaconnection.common`, `com.ideaconnection.user` |

Keycloak 경로의 `/auth`는 운영 Gateway 경로(스펙 4절)와 맞춘 것이다.

## Review Focus

1. 같은 사용자가 두 탭에서 동시에 첫 로그인: 프로필은 하나만 생기고 둘 다 200을 받는다. (Task 4)
2. 만료되거나 위조된 토큰: Problem Details 형식의 401을 받는다. (Task 2)
3. 화면을 열어 둔 사이 세션 만료: 빈 화면 없이 다시 로그인으로 이어진다. (Task 5)
4. `compose`를 내렸다 다시 실행: 실패하지 않고 realm과 가입 계정이 유지된다. (Task 1)
5. 토큰에 이름이 없음: 프로필 생성이 실패하지 않고 이메일을 이름으로 쓴다. (Task 4)

**결정한 값:**
- 에이전트에 Node와 Docker CLI를 버전 고정해 넣고 `/var/run/docker.sock`을 마운트한다. Testcontainers에 필요하다. 쓰기 권한이 있는 사람의 PR만 빌드하므로 CI 전용 VM에서 허용한다.
- `libs/common`이나 빌드 파일이 바뀌면 모든 서비스를 빌드한다. S1에는 서비스가 하나라 `services/` 변경 전체로 판단한다.

- [ ] **Step 1: 스테이지 추가**

`Check service`: `services/`(`services/web/` 제외) 변경 시 `./gradlew check`. `Check web`: `services/web/` 변경 시 `npm ci && npm run lint && npm test && npm run build`.

- [ ] **Step 2: PR 시나리오 확인**

| PR | 기대 |
| ---- | ---- |
| Java 포맷을 틀림 | `Check service` 실패 |
| web 테스트를 깨뜨림 | `Check web` 실패 |
| `docs/`만 변경 | 두 스테이지 모두 건너뜀 |
| 위 오류를 고침 | 상태 체크 성공 |

확인 후 임시 PR을 닫는다.

- [ ] **Step 3: 커밋**

```bash
git add Jenkinsfile deploy/ci
git commit -m "ci: 서비스 코드 검증 추가"
```
